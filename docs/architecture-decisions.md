### ADR-F01: The Repository Registry Is The Technical Source Of Truth, With Platform-Aware Paths

Central file: `docs/adr/fleet/`

- Status: accepted
- Decided: 2026-05-23 (registry), 2026-07-18 (platform lifecycle), 2026-09-21 (platform-aware paths)
- Consolidated 2026-11-22 from ADR-0001, ADR-0006 and ADR-0030 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Scope: `docs/repository-registry.json` and every registry-driven script
- Applies to: fleet

Context: JAMARQ has many active, parked, template, client-maintained, archived and retired repos, laid out differently on the Mac and on the Windows PCs. Agents need one technical source for lifecycle, paths, remotes, deploy model, dependency automation and security gates, and every tool needs to resolve a repo's path the same way on every machine.

Decision: **`docs/repository-registry.json` is the machine-readable source of truth.** Human docs may summarize or interpret it but never replace it.

- **Repo additions, retirements, lifecycle, deploy model and security gate changes update the registry first**, in the same PR as the docs that describe them.
- **Paths are platform-aware.** `platformOverrides.<platform>.path` replaces the default path on one platform, and the same overrides carry per-platform `status` and `securityGate`. Paths resolve in one place, `registryPathFor` / `repoPathFor` in `scripts/repo-paths.mjs`; no script reads `repo.path` itself. The validator requires an override path to be portable, to differ from the default, to stay under the default's top-level folder and to be unique per platform.
- **Lifecycle decides what work a repo gets.** Archived and retired repos get none. A `parked` repo is kept and secured but gets no feature work until the owner un-parks it.
- **Vaexil Simple Mod Framework is archived on every platform** (2026-11-13, replaced by Vaexil Mod Manager). On macOS it is never cloned, restored, inspected, built or indexed, and any live checkout is reported as drift. Immutable backup copies are not operational checkouts.

Consequences: Counts of operational repos are per platform. A sweep that reads `repo.path` directly reports false drift, so fleet sweeps go through the resolver (`docs/repository-registry.md`). The repository-registry rules in `AGENTS.md` restate this ADR.

### ADR-F02: Planning Lives In Central Markdown, Central Docs First

Central file: `docs/adr/fleet/`

- Status: accepted
- Decided: 2026-05-23; state files and plan pages added by the session workflow (`docs/session-workflow.md`)
- Consolidated 2026-11-22 from ADR-0002 and ADR-0003 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Applies to: fleet

Context: Future work needs a backlog and priority model without adding external system dependencies, and portfolio context needs one home without a `PROJECT.md` and `RUNBOOK.md` churning in every repo.

Decision: **Plans and portfolio context live in Markdown, central first.**

- **Cross-repo work** is queued in `docs/deferred-work-queue.md` in the format Atlas reads. **Project work** lives in each project's `<prefix>-project-state.md` (Next Up cards) and its one plan page.
- **Portfolio, brief, runbook, service, design and operating docs** live here in `agentic-instructions` first. A repo gets its own durable docs (an ADR file, a runbook) only when its context justifies them, and repo-local docs stay authoritative for implementation detail.
- **No GitHub Issues, Linear, Notion or other tracker** unless the owner chooses one; that choice supersedes this ADR and documents the migration.

Consequences: Planning stays portable and local, and Atlas can read all of it. Agents check the central docs before major work.

### ADR-F03: Security Exceptions Are Explicit And Expiring

Central file: `docs/adr/fleet/`

- Status: accepted
- Decided: 2026-05-23
- Consolidated 2026-11-22 from ADR-0004 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Standard: `docs/security-advisory-decisions.md`; the Tauri rules are ADR-A05
- Applies to: fleet

Context: Some advisory paths can't be fully remediated without upstream fixes or unjustified replacements, and a gate that only warns stops being read.

Decision: **Active repos use `blocking` security gates when clean, or `blocking-with-exceptions` when narrow, documented, expiring, tool-specific exceptions remain.** No active repo uses `manual`. The fix is preferred over the exception.

Consequences: Every exception is reviewed before it expires, and `docs/security-advisory-decisions.md` remains the authority for each one. The `/advisory` skill and `scripts/security-exception-expiry-check.mjs` enforce the dates.

### ADR-F04: Two-Tier Dependabot Automation Across The Fleet

Central file: `docs/adr/fleet/`

- Status: accepted
- Decided: 2026-08-18; extended 2026-08-25, 2026-09-15 and 2026-11-01; Tier B merging on internal repos 2026-11-15
- Consolidated 2026-11-22 from ADR-0021 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Standard: `docs/dependabot-automation.md`
- Applies to: fleet

Context: Dependency maintenance kept regressing into manual all-day sweeps across about 40 repos with different ecosystems and CI job names, and unattended merges of majors or of live, client or payment repos were unacceptable.

Decision: **Split the work by risk into two tiers.**

- **Tier A, GitHub-native auto-merge,** for semver minor and patch Dependabot PRs: the vendored `.github/workflows/dependabot-auto-merge.yml` (canonical copy in `templates/workflows/`) enables auto-merge, and the merge completes only once the repo's required checks pass. Every org repo in Tier A has `allow_auto_merge`, `delete_branch_on_merge` and branch protection with its own CI job required (`strict: false`, no required review, `enforce_admins: false`). `agentic-instructions` is excluded and stays human-reviewed.
- **Tier B, a prepare-and-merge resolver,** for what Tier A won't touch (majors, failing, blocked): it makes the minimal change, verifies with the repo's own scripts, and on internal repos merges after green checks (owner, 2026-11-15); elsewhere it labels `deps-ready-for-owner`. Deferrals escalate to `needs-owner-plan` on the third defer. It runs as an owner-installed local job.
- **The registry records each repo's tier** in `dependabot.autoMerge`.

Consequences: Routine updates merge on green CI with no owner step, and the owner's own merges to Tier A repos gate on CI too. Automated Dependabot merges after green checks need no owner yes (`AGENTS.md`, Git Branch Policy); any other merge does. A repo where Dependabot is unreliable documents its manual path in `docs/dependabot-automation.md` and the registry.

### ADR-F05: Apps Are Named JAMARQ <App>, Grouped By Purpose, And Folded Where They Belong Together

Central file: `docs/adr/fleet/`

- Status: accepted
- Decided: 2026-07-23 (categories), 2026-09-11 (Tenra retired), 2026-09-14 (naming), 2026-10-01 to 10-03 (folds and the shared pass), 2026-10-23 (Overlap)
- Consolidated 2026-11-22 from ADR-0005, ADR-0012, ADR-0024, ADR-0027 and ADR-0033 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Scope: every app and site in the registry
- Applies to: fleet

Context: The portfolio grew through brand families (Tenra, Vaexcore, Toolworks) that implied divisions that never existed, apps were split before anyone used them, and a brand baked into an identifier turns every brand change into a contract migration.

Decision:

- **A person reads "JAMARQ <App>"; a machine reads the bare app name.** Display name, window title and `.app` name are `JAMARQ <App>`; registry `id`, runtime manifest `appId`, root package name and storage prefixes are `<app>`; handoff schema ids are `<app>.<artifact>.v1`; the bundle id is `com.jamarq.<app>`; the repo is `JAMARQ-Digital-LLC/<App>`.
- **Products with their own identity keep their own name** with no prefix: Vicina, CrossCurrent and the Vaexcore apps (ADR-A04). JAMARQ Overlap took the prefix by the owner's choice (2026-10-23).
- **Tenra is retired** as a brand and a workspace; no app carries it. Software is sold under JAMARQ. `tenra.dev` is an art site, with the old business site archived in its repo.
- **Every `Apps/` repo has a purpose category** (`appCategory`: Business, Community, Finance/Records, Gaming, Operations, Research, Utility), separate from workspace, ownership, brand and product line.
- **Apps fold where their functions belong together**, and stay separate where they don't, each for a stated reason. A fold renames inside the fold, archives the absorbed repo only after its successor merges, verifies and is installed, and moves its registry entry to `archive` in the same governance PR. Folding merges products, not shared infrastructure; the apps that remain stay alike behind the scenes.

Consequences:

- **A bundle id change is a migration** for any app that has shipped: it orphans identifier-keyed data and macOS permission grants and changes the Windows upgrade key, so a shipped app needs a migration note.
- **A renamed schema id is not aliased** unless a consumer holds stored payloads under the old id.
- **Renames are checked everywhere** a name appears, and history (the decision log, archived ADRs, dated notes) keeps the names it was written with.
- **The fold record** (nine folds, 2026-10-01 to 10-03) is in the archive under ADR-0033 and in the decision log.

### ADR-F06: Self-Hosted CI Runs On A Linux Pool On JASON-PC-2

Central file: `docs/adr/fleet/`

- Status: accepted
- Decided: 2026-09-12 and 2026-09-22; moved to JASON-PC-2 2026-10-07; cut to four runners 2026-11-17; Proxmox switchover planned 2026-11-21
- Consolidated 2026-11-22 from ADR-0032 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Scope: every workflow in `JAMARQ-Digital-LLC` that runs on a self-hosted runner
- Runbooks: `docs/runner-fleet-windows-migration.md`, `docs/runner-host-proxmox-plan.md`
- Applies to: fleet

Context: Self-hosted jobs ran on Mac runners, and in September 2026 the org exhausted its included hosted minutes under a hard-stop budget.

Decision: **Self-hosted jobs run on a Linux pool on JASON-PC-2,** selected with `[self-hosted, Linux, X64, jamarq-win]`. Today that is four runners, `jamarq-pc2-1`, `-2`, `-7` and `-8`, in one Hyper-V Ubuntu VM on its own NAT network with switch ACLs blocking the LAN and the host. Every movable hosted job in a private repo runs there.

- **Stays on GitHub-hosted runners:** public repos (the three Slint apps among them), the monitors that must outlive the pool, Windows and macOS jobs, the clean-image Tauri platform reviews, and deploy or release jobs.
- **A move to Proxmox is planned** (owner, 2026-11-21): six runners, `jamarq-pc2-1` to `-6`, in one Proxmox guest replace the Hyper-V VM. Until the switchover the Hyper-V pool is what runs, and the switchover PR amends this ADR.

Consequences:

- **CI does not build macOS app bundles;** that is a local step before a Mac release.
- **The runners share one machine,** so jobs never use fixed service ports, never install into a shared tool cache or system path, and allow for a loaded machine. Each runner has its own tool cache.
- **All runners offline at once means the host,** not the jobs. The fleet monitor runs every four hours.

### ADR-F07: Google APIs Sign In As The Owner, Not A Service Account

Central file: `docs/adr/fleet/`

- Status: accepted
- Decided: 2026-10-26
- Consolidated 2026-11-22 from ADR-0035 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Applies to: fleet

Context: Reading Search Console and similar Google data was planned through service accounts with downloaded JSON keys. The organization enforces `iam.disableServiceAccountKeyCreation`, a downloaded key is a long-lived private key that works from anywhere, and each service account needs its own grant per property.

Decision: **Anything that would use a service account to reach Google data the owner can already reach signs in as the owner instead.**

- One OAuth client of type Desktop app per app or tool, in that app's own project.
- PKCE, the narrowest read scopes, `access_type=offline`, and a loopback redirect.
- The client file and refresh token live in the macOS Keychain for desktop apps, or the machine-local `~/.config/jamarq/*.env` store for a CLI (`docs/local-provider-access.md`), never in a repo, a CLI argument or a log.
- Disconnect revokes the token at Google.
- A service account is used only where no person can sign in, and that exception is the owner's call, recorded here.

Consequences: No key policy exceptions and no per-property grants. In Testing, Google ends a sign-in after 7 days, so apps say so plainly and offer Connect again. The `gsc` CLI's service-account key is still queued to move (`[gsc-owner-sign-in]`).

### ADR-F08: One Formatter Per Language

Central file: `docs/adr/fleet/`

- Status: accepted
- Decided: 2026-11-22
- Standard: `docs/design-product-standards.md`
- Scope: JAMARQ repositories
- Applies to: fleet

Context: The 2026-11-22 inventory of 45 operational Mac repos found ten using Prettier checks, 25 running ESLint, six running `cargo fmt --check` and 12 relying on `.editorconfig` alone. The fleet standards had no formatting rule. Triage had no Prettier config, and on 2026-11-12 a `prettier --write` pass turned two small fixes into 500- and 2,700-line diffs.

The owner considered Biome (partial, opt-in Astro and HTML support, new opt-in Markdown support, and the need to keep ESLint for Next.js rules), dprint (less familiar, downloads plugins on demand and has limited Astro coverage for the fleet's needs), and leaving formatting to editors (CI could not catch drift).

Decision: **Use Prettier for web files in repos that already have a `package.json`, and rustfmt for Rust.**

- **Web files.** Prettier formats TypeScript, JavaScript, JSON, CSS, Astro, Markdown and YAML. Use Prettier defaults in `.prettierrc`, with `proseWrap: "preserve"` explicit so Markdown prose keeps its line breaks while lists and tables can be normalized. Astro repos add `prettier-plugin-astro` and select the `astro` parser for `*.astro`.
- **Rust.** Run `cargo fmt --check` in each Rust repo's existing `lint` or `verify` step.
- **Linting.** Keep ESLint for lint rules, including Next.js rules. Where ESLint has layout rules, use `eslint-config-prettier` to disable rules that conflict with the formatter.
- **Node scope.** A repo without a `package.json`, such as a PowerShell, PHP-only or docs-only repo, keeps its existing toolchain for formatting.
- **Exclusions.** Keep generated and copied files out of formatter passes. In `.prettierignore`, include `docs/architecture-decisions.md` (its generated section has a SHA-256 record from `scripts/adr-sync.mjs`), `src/agent_kit/`, `src/agent-kit/`, copied pairing folders, `*.sha256`, lockfiles and build output. In `jamarq-agent-kit`, exclude the reference module folders as well to preserve the hashes consumers check. Keep copied Rust modules out of rustfmt's input too.
- **Adoption.** Use one format-only PR per repo. Provide `format` as `prettier --write .` and run `prettier --check .` through the existing `lint` or `verify` step. Use `format:check` when `lint` already runs ESLint. Add checks to the existing CI job and keep the PR free of behavior changes and unrelated edits.
- **Games.** Choose a GDScript formatter when the first game is promoted from prototype (`docs/game-dev-standard.md`).

Consequences: Most existing Prettier users already use the default style. DMARC Reports has a 100-column override, so the shared style keeps the smaller default configuration. The rollout in `[formatter-adoption]` begins after this ADR merges, and each repo waits for its ADR-sweep PR before adopting the formatter. CI can then flag drift through the repo's existing checks.

### ADR-A01: Desktop Apps Are Thin Shells Over Plain Rust Cores, Built To One Standard

Central file: `docs/adr/apps/`

- Status: accepted
- Decided: 2026-08-22 (converge on Tauri), 2026-10-24 (Slint for Windows-native), 2026-11-18 (Rust back ends), 2026-11-22 (the standard, owner approving agentic-instructions#660)
- Consolidated 2026-11-22 from ADR-0022, ADR-0034, ADR-0038 and the release rules of ADR-0026 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Standard: `docs/desktop-app-standard.md` (restates this ADR)
- Scope: every active desktop app, Tauri and Slint, and every new one
- Review date: when the first native shell replaces a Tauri shell, or 2027-05-22, whichever comes first
- Applies to: apps, linecheck, dragoman, remy, deskcheck

Context: The owner set the fleet's end state on 2026-11-22: "macOS native build for MacOS, Windows native build for Windows, with a shared surface for both of them to draw from", each "the absolute most optimized option for each platform, without sacrificing features", with "Tauri/Rust is the current direction for purposes of standardization". Electron apps were 263 to 301 MB against Tauri's 8.6 to 12 MB, and the inventory of 2026-11-22 found sixteen of seventeen Tauri apps were one `tauri` crate with logic in commands or the page, infrastructure copied by hand without records, and tests and dev builds that could reach real data.

Decision: **Every desktop app is a thin window over plain Rust core crates, and is built, run, tested and released to `docs/desktop-app-standard.md`.**

- **The stack follows where the app ships.** Mac-first and multi-platform apps are Tauri; Windows-native apps are Rust and Slint, laid out like Modlist Launcher. Electron is not allowed. No app migrates only because of this.
- **The core is plain Rust** with no window, webview or Node dependency; Tauri commands and Slint callbacks are adapters; the page is presentation only. An app is done when its logic is in a core crate, not only when its back end is Rust.
- **Shared infrastructure is copied byte-identical from `jamarq-app-kit` with hash records** (the ADR-A02 pattern), checked by one conformance script. No shared crate is published; the Slint `theme.slint` is one of the copied modules.
- **Every app has the same script names, a scratch-safe `verify`, a `.dev` bundle id for dev and scratch builds, a hidden-launch smoke on the Mac, SemVer, release only when the owner asks (with `main-build.yml`), and the same CI layout.**
- **Shipped targets are set per app,** and each app's shipped targets decide which advisory platforms are in scope.
- **The native end state is reached app by app:** core crates first, then CrossCurrent proves a SwiftUI shell over its core through UniFFI and Mixtape follows, then the other Mac-first apps, then the multi-platform apps. Slint stays the Windows-native shell.
- **Dependencies are classed crucial, useful or extra,** and extra ones go, weighed against the work each removal adds.

Consequences:

- **Most apps need a core-crate extraction,** the largest piece of the standard, sized per app on the App Standard plan page.
- **The desktop smoke is the hidden launch** (`smoke-hidden` from the app kit); `tauri-driver` is used only by the platform reviews (ADR-A05).
- **The Mac native pilot is a local build** installed through Atlas's Reinstall; CI tests the core crates.
- **Slint brings no dependency saving** over Tauri; its case is a Rust-only Windows shell.
- **Revisit** if UniFFI or SwiftUI can't carry an app's features, if the owner chooses WinUI over Slint, or if the conformance check costs more than the drift it catches.

### ADR-A02: Apps Take Agent Interfaces From One Copied Kit

Central file: `docs/adr/apps/`

- Status: accepted
- Decided: 2026-11-13; kit v8 dropped `rmcp` 2026-11-17
- Consolidated 2026-11-22 from ADR-0036 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Standard: `docs/agent-interfaces.md`
- Applies to: apps, jamarq-agent-kit

Context: The owner approved structured AI operation (headless engine, typed error codes, a JSON command line, plan/apply with a journal, a stdio MCP server and a redacted `diagnose`) for 16 apps on 2026-11-13. Built separately, each app would re-derive a plan that is exactly what the write does, and the safety rules would drift.

Decision: **One kit, copied byte-identical, with a standard.**

- `JAMARQ-Digital-LLC/jamarq-agent-kit` holds the reference: a Rust half with its own stdio JSON-RPC MCP server on `serde`, `serde_json`, `sha2` and `schemars` only, with no async runtime, and a TypeScript half on `@modelcontextprotocol/sdk`, with the same codes, JSON shapes, content hash and redaction rules.
- Apps copy one half with its record, `agent-kit.sha256`, and never edit the copy; each copy's test checks it against its record, and the conformance check names copies behind.
- The app keeps everything that names it outside the copy: its codes, data folder, `aiChanges` setting, tools and instructions.
- The MCP server is a stdio process, not a listener. Where an app serves a loopback API, the MCP process is its client, and the server keeps the Loopback Server Guard and the AI gate.

Consequences: The safety rules are code: the plan store and journal require the `Authorized` value only the AI write gate issues. A kit change costs a PR in the kit and one per adopting app. The kit proves itself in its own CI first. AI writes are off by default and nothing irreversible becomes a tool. Vaexil Mod Manager still runs its own original on `rmcp` until it adopts the kit (`[vmm-adopts-agent-kit]`).

### ADR-A03: Every JAMARQ App Connects To Another Through The Pairing Module

Central file: `docs/adr/apps/`

- Status: accepted
- Decided: 2026-07-22 (receiving-side handoff model), 2026-11-14 (pairing), 2026-11-22 (a held port is an error)
- Consolidated 2026-11-22 from ADR-0010 and ADR-0037 (`docs/adr/archive/architecture-decisions-0001-0040.md`)
- Standard: `docs/standalone-connectable-app-standard.md`; adoption rules in the archive under ADR-0037
- Applies to: apps

Context: On 2026-11-14 the fleet had four ways for one app to reach another (the pairing module, plain HTTP with no or a shared key, copy and paste, and Vaexcore's status files and environment-variable keys), and only one proved who was calling.

Decision: **The pairing module is the one way any two JAMARQ apps connect.**

- An app that calls or is called by another carries the module (`src-tauri/src/pairing/`, byte-identical, with `pairing-module.sha256`) and its own `connections.rs`. A caller finds the other app through its named offers, never a fixed port, an environment variable or a pasted key.
- **A called app checks the bearer key against its pairings;** a request that names its sender must match the paired caller.
- **An app that offers an address keeps it stable** and never falls back silently to another port; a held port is an error shown in Settings (`loopback-guard`).
- **Status files and health probes show status only** and never authenticate anything.
- **No shared or per-machine credentials between apps.** Keys stay in the signed shell (Keychain, Credential Manager); a page never sees one.
- **The receiving side owns a durable pending preview and append-only history,** replay of an identical record is idempotent, and intake never confirms, sends on or acts.
- **Copy and paste stays only as a fallback** under More.

Consequences: Windows needs its own peer check (a per-user named pipe, same user SID, install-path check, keys in Credential Manager), built and tested on Windows before any app uses it. One module change means one PR per adopting app. Review when the module has a Windows back end whether it moves into its own repository.
